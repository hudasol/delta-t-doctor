# Security and data handling

* **Nothing is stored.** Uploads are read into memory, analysed and discarded. There is no database, no log of file
  contents and no user accounts.
* **No outbound calls.** The web app bundles its fonts and scripts and makes no external requests, so it can run
  on an isolated network.
* **Limits.** 25 MB per upload (read in a bounded way), 2 million rows, 200 columns, 150 MB unpacked for .xlsx (zip-bomb check), 500 buildings per portfolio file, a concurrency cap (`DTD_MAX_CONCURRENT`, default 4, 2 in the Docker image) that returns 503 when full, and finite-number validation on all contract terms. Old `.xls` files are refused.
* **Input quality gate.** Spikes, sensor codes (-999, 99.9 and similar), impossible temperatures, unreadable timestamps and frozen meters are removed or flagged, counted in `data_quality.input`, and make `reliable` false above small thresholds. A 1% flow-spike file moves the surcharge estimate by 0.1%, against a factor of 40,000 before this check.
* **Audit log.** Each API call writes one JSON line (request id, path, status, duration) and each upload one line (size, first 16 hex of its SHA-256, truncated filename). File contents are never logged. Responses carry `X-Request-ID`.
* **Output.** Portfolio CSVs prefix cells that start with `= + - @` so a building name cannot run as a spreadsheet formula.
* **Headers.** `nosniff`, `X-Frame-Options: DENY`, `no-referrer`, `no-store`, and a Content-Security-Policy limited to
  the app's own origin (inline script and style are allowed because the UI is a single file).
* **Container.** The image is built in two stages: the first downloads every dependency as a wheel checked against the sha256 hashes in the generated `requirements.lock`; the second installs from those wheels with networking disabled (`RUN --network=none`, `--no-index --require-hashes`). It runs as a numeric non-root user with no home directory and no login shell, and has a health check. It also runs read-only, with a small in-memory `/tmp` for upload spooling: `docker run --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m --cap-drop ALL --security-opt no-new-privileges -p 8000:8000 delta-t-doctor` (the CI smoke test runs exactly this and posts an upload).
* **Not included.** Authentication, TLS and rate limiting. Run it behind your own reverse proxy or API gateway
  (see [DEPLOYMENT.md](DEPLOYMENT.md)). Do not expose it to the public internet as it is.
* **Model files.** `joblib` files can run code when loaded. A bundled model is loaded only if its bytes match the sha256 in `model_card.json` (missing entry means refuse) and the installed scikit-learn has the same minor version as at training. That is integrity, not authenticity: someone who can rewrite both files can still swap the model, so verify release artefacts out of band and never point the app at a model file from an untrusted source. A model path outside the package logs a warning and is not verified.
* **Known gaps.** `script-src` still allows `'unsafe-inline'` (single-file UI; planned to move to a nonce). No container image vulnerability scan is run. No authentication or TLS. Closed in v1.2.0: GitHub Actions are pinned to commit SHAs, `requirements.lock` is generated with hashes for every dependency (it replaces the hand-written `requirements-lock.txt`, which pinned only 12 top-level packages and left transitive ones open), and a CycloneDX SBOM (`sbom.cdx.json`) is generated from it with `make sbom`.
* **Reporting a problem.** Open a GitHub issue without any customer data in it.
* **Upload limits.** A 25 MB read cap applies to every upload, and POST bodies whose Content-Length exceeds 26 MB are rejected before parsing. Starlette spools multipart bodies to disk before the handler runs, and chunked requests carry no Content-Length. Since v1.1.1 a pure-ASGI middleware (`BodyLimit`) counts request bytes as they arrive and answers 413 once the 26 MB limit is passed, whether or not Content-Length was sent (`tests/test_upload_cap.py`). Still set a body-size limit on the reverse proxy as well: it stops the bytes before they reach the app. Heavy routes (parse, simulate, diagnose, demos) share a concurrency limit and return 503 when full.

## Threat model (v1.2.0)

Scope: the package, the CLI, the web app and the Docker image as shipped in this repository. Out of scope: the reverse proxy, the host and
the network around it, which the operator provides (see [DEPLOYMENT.md](DEPLOYMENT.md)).

| Asset or entry point | Threat | Control in the product | Test or evidence | Residual risk |
|---|---|---|---|---|
| Uploaded meter files (CSV, .xlsx) are untrusted | Parser exhaustion, zip bombs, formula injection in outputs, malformed numbers | 25 MB read cap and streaming body limit (413), 2 million rows, 200 columns, 150 MB unpacked .xlsx and zip bomb check, `.xls` refused, sentinel and range checks, formula prefixing in CSV output | `tests/test_upload_cap.py`, `tests/test_edge_robustness.py`, `tests/test_io.py` | A crafted file within the limits can still cost seconds of CPU; the concurrency cap returns 503 rather than queueing |
| Bundled model files (`joblib`, which can execute code when loaded) | A swapped or corrupted model file | Bytes are hashed and compared with the sha256 in `model_card.json` before unpickling; missing entry means refuse; scikit-learn minor version must match | `tests/test_edge_robustness.py::test_tampered_bundled_model_refused` | Integrity, not authenticity: whoever can rewrite both the model and the card can swap the model. Verify release artefacts out of band |
| Fleet calibrated models (`deltat-doctor calibrate`, new in v1.2.0) | A tampered calibrated file, or a calibrated model silently replacing the default | A sidecar `<model>.card.json` carries the sha256 and is checked before unpickling (fail closed); `calibrate` refuses to write into the package assets; a calibrated model is used only with an explicit `--model`; the web API always uses the bundled model | `tests/test_calibrate.py` (tamper, assets refusal, default model unchanged) | A model file with no card loads with a warning, as before; only load models you built |
| Base training rows for calibration (`assets/calibration_base.npz`) | Poisoned rows that bias every calibrated model | sha256 recorded in the model card and checked (fail closed); loaded with `allow_pickle=False` | `tests/test_calibrate.py` uses the same loader path | Same integrity, not authenticity, limit as the models |
| Network egress | Data leaving the site | The product makes no network calls at runtime: fonts and scripts are bundled, no telemetry; `scripts/fetch_real_data.py` is a research script and is not part of the package | `tests/test_v02_portfolio_report.py` (no external references in the UI), `tests/test_assurance.py` (a diagnosis runs with outbound sockets disabled) | Operator must still restrict egress at the host or container level |
| Denial of service | Large or many requests | Body limits above, row and column caps, `DTD_MAX_CONCURRENT` (503 when full), portfolio cap of 500 buildings | `tests/test_upload_cap.py` | No rate limiting or authentication in the app; put both on the proxy |
| Supply chain | A changed dependency between builds | `requirements.lock` is generated by `scripts/make_lock.py` (pip resolves the runtime extras; PyPI's published sha256 digests for every file of each pinned version) and covers every package, direct and transitive, and the Docker image installs with `--require-hashes` and `--no-index` from a wheel stage; an SBOM (`sbom.cdx.json`, CycloneDX) lists every component | `.github/workflows/ci.yml` builds the image and runs a smoke test | Hashes pin what PyPI served when the lock was made; they do not prove those packages are benign. GitHub Actions are pinned to commit SHAs |
| Container runtime | Escalation from the app process | Numeric non root user, no home and no login shell, runs with `--read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges` | CI smoke test runs the image that way, including an upload | Not scanned for CVEs in CI (no image scanner is run) |

**Standards.** The controls above are written with these frameworks in mind. This is an intended mapping, **not a certification or
a compliance claim**, and no assessment has been done: OWASP ASVS (input validation, file upload, configuration), NIST SSDF SP 800-218
(PS.2 and PS.3 for release integrity and provenance, PW.4 for dependency reuse), SLSA build level concepts (provenance, pinned
dependencies), and the UAE Information Assurance Regulation as a reference for the operator's own controls.
